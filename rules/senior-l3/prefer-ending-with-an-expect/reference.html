prefer-ending-with-an-expect

L3 — Senior Test Completeness Assertion Strategy Actionability vs Correctness

Why this rule exists

Playwright tests that end with an action (click, fill, goto, etc.) rather than an assertion express no verifiable outcome — the test can pass even when the feature is completely broken, because Playwright will simply execute the action without confirming anything changed. This is especially dangerous because Playwright's auto-waiting resolves on interaction readiness, not on post-interaction correctness: a click() that succeeds proves the element was clickable, not that the click produced the expected result.

What interviewers look for

  • The candidate distinguishes between Playwright's auto-waiting (waits for actionability before an action) and assertions (verify state after an action), and explains why auto-waiting alone is insufficient as a correctness check.
  • The candidate can identify subtle action-ending patterns — not just bare page.goto() calls, but cases like page.getByRole('button').click() following an expect, where the expect is present but misplaced as a non-final statement.
  • The candidate knows about the assertFunctionNames and assertFunctionPatterns escape hatches and can explain when a custom assertion helper wrapper is the right solution versus inline expect calls.

Examples

Bad — Login flow ending on a click BAD 1 
test('user can submit the login form', async ({ page }) => {
  await page.goto('/login');

  await expect(page.getByLabel('Email')).toBeVisible();

  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('hunter2');
  await page.getByRole('button', { name: 'Sign in' }).click(); // no post-submit assertion
});
What's wrong: The test ends on click(), so it only verifies that the button was clickable — it never confirms the login actually succeeded (e.g., redirect to /dashboard or appearance of a welcome message). A regression that breaks the POST handler would not be caught.
Bad — API intercept setup with a misplaced assertion BAD 2 
test('search results load after query', async ({ page }) => {
  await page.route('/api/search*', async (route) => {
    await route.fulfill({ json: { results: [{ id: 1, title: 'Widget' }] } });
  });

  // expect is present but verifies an intermediate state — not the final outcome
  await expect(page.getByRole('heading', { name: 'Search' })).toBeVisible();

  await page.goto('/search');
  await page.getByRole('searchbox').fill('widget');
  await page.getByRole('button', { name: 'Search' }).click(); // test ends here
});
What's wrong: The expect is present but verifies the heading before the search is even triggered. The test ends on the click() that fires the search — there is no assertion that the mocked results actually rendered.
Good — Login flow with a post-submit assertion GOOD 1 
test('user can submit the login form', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('hunter2');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await expect(page).toHaveURL('/dashboard'); // observable outcome verified
});
Why this works: The final statement asserts the observable outcome — a URL change to /dashboard — giving the test a real contract. A broken auth handler will now cause the test to fail rather than pass silently.
Good — Search results verified via a custom assertion helper GOOD 2 
import { test } from '@playwright/test';
import { assertResultCount } from '../helpers/search-assertions';

test('search returns matching products', async ({ page }) => {
  await page.route('/api/search*', async (route) => {
    await route.fulfill({
      json: { results: [{ id: 1, title: 'Widget' }, { id: 2, title: 'Gadget' }] },
    });
  });

  await page.goto('/search');
  await page.getByRole('searchbox').fill('widget');
  await page.getByRole('button', { name: 'Search' }).click();

  await assertResultCount(page, 2); // helper registered via assertFunctionNames option
});
Why this works: The custom helper assertResultCount encapsulates a reusable assertion pattern, and the assertFunctionNames ESLint option tells the linter to treat it as an assertion. The test ends on a meaningful check without requiring the helper to be inlined.

Interview talking points

Gotcha question

"Our test has an expect in the middle of the body and a click() at the end. The expect passes. Why would this rule still flag the test, and is the rule being overly strict here?"

Expected senior answer

The rule flags the test because the final statement is an action, not an assertion — the expect earlier in the body proves something about an intermediate state, not the outcome of the last action. This is not overly strict: every action can produce a side effect, and the only way to confirm that side effect is with an assertion. The fix is to either add an assertion after the click() that verifies its result, or reorder the test so the meaningful assertion comes last.

Common misconception

Junior/mid candidates often argue that "Playwright's auto-waiting handles this" — believing that if click() resolves without timing out, the feature must be working. This conflates actionability (can I interact with this element?) with correctness (did the interaction produce the right outcome?). Auto-waiting waits for an element to be stable and interactable; it does not verify what happens after the interaction completes.
