Playwright SDET Interview · L3 Senior · Flakiness & Hard-coded Delays

no-wait-for-timeout

L3 — Senior Flakiness Hard-coded Delay Dumb Sleep

Why this rule exists

page.waitForTimeout is a dumb sleep: it pauses the test for a fixed wall-clock duration with no awareness of browser state, network conditions, or CI machine speed, making tests both slower than necessary and still prone to failure when the system is slower than expected. Playwright's execution model is built around auto-retrying, event-driven assertions — waitForSelector, waitForResponse, waitForURL, etc. — that resolve the moment the condition is true and throw a meaningful error when the timeout elapses. Hard-coded delays hide the real signal that the test should be waiting for, mask the root cause of flakiness instead of fixing it, and inflate suite duration linearly with every added sleep across a large test suite.

What interviewers look for

  • The candidate can name specific Playwright APIs that replace waitForTimeout and explain which signal each one waits on (DOM readiness, network idle, URL change, JS expression, element visibility).
  • The candidate understands that waitForTimeout is a smell pointing to a missing explicit wait, and can diagnose what the underlying race condition actually is rather than just substituting a different API mechanically.
  • The candidate can articulate the trade-off between correctness and speed: a fixed delay that is "long enough" today becomes a bottleneck over time, while an event-driven wait exits as soon as the condition is met — both faster on average and more reliable under load.

Examples

Bad — Waiting for a spinner to disappear after form submit BAD 1 
test('submitting the login form navigates to the dashboard', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('s3cr3t!');
  await page.getByRole('button', { name: 'Sign in' }).click();

  // Guess at server response time — races on slow CI, wastes time on fast machines
  await page.waitForTimeout(3000);

  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});
What's wrong: The 3-second sleep is a guess at how long the network round-trip and redirect take. On a slow CI runner it will still race, and on a fast machine it wastes 3 seconds every run. The test should wait for an observable browser signal — the URL change or the heading becoming visible — both of which Playwright already retries automatically.
Bad — Polling for a toast notification after an API action BAD 2 
test('deleting a record shows a success toast', async ({ page }) => {
  await page.goto('/settings/users');

  await page.getByRole('row', { name: 'Jane Doe' }).getByRole('button', { name: 'Delete' }).click();
  await page.getByRole('button', { name: 'Confirm' }).click();

  // Arbitrary buffer racing against animation AND server latency simultaneously
  await page.waitForTimeout(1500);

  await expect(page.getByRole('alert')).toHaveText('User deleted successfully');
});
What's wrong: The 1.5-second delay is an arbitrary buffer that races against animation timing and server latency simultaneously. expect(toast).toHaveText(...) already retries on its own — removing the sleep entirely lets Playwright wait the right amount of time automatically.
Good — Wait for URL change after login GOOD 1 
test('submitting the login form navigates to the dashboard', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('s3cr3t!');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await page.waitForURL('/dashboard'); // resolves the instant the URL changes

  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});
Why this works: waitForURL resolves the instant the browser navigates to the target URL and throws a descriptive error if it never does — no wasted time on fast machines and no flakiness on slow ones.
Good — Wait for the network response that triggers the toast GOOD 2 
test('deleting a record shows a success toast', async ({ page }) => {
  await page.goto('/settings/users');

  const deleteResponse = page.waitForResponse(
    (resp) => resp.url().includes('/api/users/') && resp.request().method() === 'DELETE'
  );

  await page.getByRole('row', { name: 'Jane Doe' }).getByRole('button', { name: 'Delete' }).click();
  await page.getByRole('button', { name: 'Confirm' }).click();

  await deleteResponse; // synchronise on the real signal

  await expect(page.getByRole('alert')).toHaveText('User deleted successfully');
});
Why this works: By awaiting the specific network response that drives the UI update, the test synchronises on the real signal rather than a guess. The toast assertion then benefits from Playwright's built-in auto-retry, making the test as fast as the server and as resilient as the event it actually depends on.

Interview talking points

Gotcha question

"Our app has a CSS animation that delays an element becoming interactive by 400 ms — waitForTimeout(500) makes the test pass reliably. Isn't that a legitimate use?"

Expected senior answer

Push back on the framing: the correct fix is to wait for the element to be enabled or stable using waitFor({ state: 'stable' }) or toBeEnabled(), which polls until the animation settles. If the app intentionally gates interactivity behind an animation, the test should assert on that observable state — not guess at its duration. Playwright's actionability checks already wait for elements to stop moving before clicking, so the sleep may not even be doing what the author thinks.

Common misconception

Junior/mid candidates often treat waitForTimeout as a safe fallback for "I'm not sure what to wait for," not realising that Playwright's locator-based assertions (toBeVisible, toHaveText, toBeEnabled) all auto-retry for up to the configured timeout by default — meaning the explicit sleep is redundant in the best case and still racy in the worst.
