L3 — Senior Async Correctness Promise Lifecycle Floating Callbacks

Why this rule exists

Playwright's test runner tracks assertions by awaiting the promises they return. If a .then() callback containing an expect() is neither awaited nor returned from the test function, the test body finishes before the assertion ever executes — producing a false-green. Chained promises stored in variables but then branched into new .then() calls without re-assigning or returning the chain suffer the same fate — the final promise that carries the assertion floats free and its result is discarded.

What interviewers look for

  • The candidate can explain that unawaited .then() callbacks with expectations silently swallow assertion failures because the test runner completes before the microtask resolves.
  • The candidate understands that returning a promise is a valid alternative to await — the runner will wait on anything the test function returns — and knows when each style is appropriate.
  • The candidate recognizes that chaining additional .then() calls off a previously-resolved intermediate variable creates a new dangling promise unless the variable is reassigned and the final value is returned.

Examples

Bad — Floating intercept assertion BAD 1 
test('API response contains correct user data after login', ({ page }) => {
  page.route('/api/auth/login', async (route) => {
    await route.fulfill({ json: { userId: 42, role: 'admin' } });
  });

  page.goto('/login').then(async () => {  // not awaited or returned
    await page.fill('[data-testid="email"]', 'admin@example.com');
    await page.fill('[data-testid="password"]', 'hunter2');
    await page.click('[data-testid="submit"]');
  });

  page.waitForResponse('/api/auth/login').then((response) => {  // also not awaited
    expect(response.status()).toBe(200);
    expect(response.json()).resolves.toHaveProperty('role', 'admin');
  });
});
What's wrong: Neither .then() chain is awaited or returned, so both promises detach from the test lifecycle. The assertions inside the second .then() will never be evaluated — status code mismatches or missing response fields will not cause the test to fail.
Bad — Broken reassignment chain BAD 2 
test('form submission triggers confirmation toast', ({ page }) => {
  const navPromise = page.goto('/settings/profile').then(async () => {
    await page.fill('[data-testid="display-name"]', 'Jane Doe');
    await page.click('[data-testid="save-button"]');
  });

  navPromise.then(async () => {  // creates a new promise — not reassigned, not returned
    const toast = page.locator('[data-testid="toast"]');
    await expect(toast).toBeVisible();
    await expect(toast).toContainText('Profile updated');
  });

  return navPromise; // resolves before the second .then() runs
});
What's wrong: A second .then() is chained off navPromise but assigned to nothing — it creates a new, separate promise that is never returned. The test returns navPromise, which resolves before the second .then() runs, so the toast assertions execute after the runner has already marked the test as passed.
Good — Full chain awaited with async/await GOOD 1 
test('API response contains correct user data after login', async ({ page }) => {
  await page.route('/api/auth/login', async (route) => {
    await route.fulfill({ json: { userId: 42, role: 'admin' } });
  });

  await page.goto('/login');
  await page.fill('[data-testid="email"]', 'admin@example.com');
  await page.fill('[data-testid="password"]', 'hunter2');

  const [response] = await Promise.all([
    page.waitForResponse('/api/auth/login'),
    page.click('[data-testid="submit"]'),
  ]);

  expect(response.status()).toBe(200);
  await expect(response.json()).resolves.toHaveProperty('role', 'admin');
});
Why this works: Every asynchronous operation is awaited directly, so assertions run inside the same synchronous flow that the test runner controls. There are no floating callbacks; any assertion failure immediately rejects the async function and is surfaced as a test failure.
Good — Reassigned chain returned explicitly GOOD 2 
test('form submission triggers confirmation toast', ({ page }) => {
  let chain = page.goto('/settings/profile').then(async () => {
    await page.fill('[data-testid="display-name"]', 'Jane Doe');
    await page.click('[data-testid="save-button"]');
  });

  chain = chain.then(async () => {  // reassigned back to chain
    const toast = page.locator('[data-testid="toast"]');
    await expect(toast).toBeVisible();
    await expect(toast).toContainText('Profile updated');
  });

  return chain; // tail of the full sequence — captures all assertion failures
});
Why this works: Each .then() is immediately reassigned back to chain, so the variable always holds the tail of the promise sequence. Returning chain hands the fully-linked promise to the test runner, which correctly captures any assertion failures anywhere in the chain.

Interview talking points

Gotcha question

"This test never fails even though the element doesn't exist — why?" (Show a test with page.locator(...).then(el => expect(el).toBeVisible()) that is neither awaited nor returned.)

Expected senior answer

The .then() callback runs as a microtask after the test function has already returned undefined. The runner sees no promise to wait on, marks the test green, and the rejection from toBeVisible() is an unhandled promise rejection that may not even surface in the console depending on Node.js version. The fix is either return the promise or convert to async/await.

Common misconception

Junior/mid candidates often believe that as long as the code inside .then() uses await, the outer promise is automatically tracked by the test runner. They conflate "the inner async work is sequential" with "the outer promise is anchored to the test." The inner await only serializes work within that callback — it does nothing to attach the resulting promise to the runner unless the callback's return value is awaited or returned at the test level.
